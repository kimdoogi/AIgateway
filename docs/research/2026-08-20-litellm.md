## A. 허브 포맷과 디스패치 구조

**OpenAI Chat Completions가 canonical 포맷이다 — 단, 이미 오염된 형태로.** `completion()`의 시그니처(`litellm/main.py:4901`)는 OpenAI 파라미터를 그대로 나열하는데, 그 안에 `thinking: AnthropicThinkingParam | None = None`(main.py:4948)이 최상위 파라미터로 들어가 있다. Anthropic 방언이 "유니버설" 시그니처로 승격된 것이다. 이 `thinking` 파라미터는 Gemini config의 supported params에도 등장한다 — 허브 포맷이 특정 프로바이더 방언을 흡수하며 자라는 전형적 부식 패턴.

**디스패치는 거대 분기문 + 최근 리팩토링의 혼합물이다.** 구조는 3세대가 공존한다:

1. **구세대**: `completion()` 내부의 `if custom_llm_provider == "azure": ... elif ...` 체인. `elif custom_llm_provider` 분기가 main.py에만 104개 (completion + embedding 합산).
2. **중간 리팩토링**: 각 분기가 `_CompletionDispatchContext` frozen dataclass(main.py:5542)를 받는 `_complete_anthropic`(main.py:2731), `_complete_bedrock`(main.py:3939) 같은 60여 개의 per-provider 헬퍼 함수로 추출됨. 분기문 자체는 남아 있고, 각 헬퍼는 ctx에서 필드를 다시 15줄씩 언패킹한다.
3. **신세대 (BaseConfig 패턴)**: `litellm/llms/base_llm/chat/transformation.py`의 `BaseConfig` ABC (447줄). 핵심 추상 메서드는 `get_supported_openai_params` / `map_openai_params` / `transform_request` / `transform_response` / `validate_environment` / `get_error_class`이고, 그 외 `sign_request`(Bedrock SigV4용), `get_model_response_iterator`, `should_fake_stream`, `calculate_additional_costs` 등 20여 개의 훅. `ProviderConfigManager._build_provider_config_map`(utils.py:7790)이 `LlmProviders → (factory, needs_model)` dict 레지스트리를 만들고, 공용 `BaseLLMHTTPHandler`(main.py:316)가 config를 받아 HTTP를 수행한다. **이게 정확히 N+M 어댑터 구조다** — 다만 절반만 이주됐다.

이주가 미완인 증거: OpenAI 자신조차 기본으로는 generic handler를 안 탄다 — `EXPERIMENTAL_OPENAI_BASE_LLM_HTTP_HANDLER` 환경변수 플래그가 있다(main.py:2514). Anthropic은 `anthropic_chat_completions.completion`(구식 handler 클래스)을 여전히 경유한다(main.py:2768).

**프로바이더 하나 추가 시 손대는 지점 (실측)**: ① `llms/<provider>/chat/transformation.py` config 클래스 ② `litellm/__init__.py` export ③ `types/utils.py`의 `LlmProviders` enum ④ `ProviderConfigManager` 맵 ⑤ main.py 디스패치 분기 + `_complete_*` 함수 ⑥ (특수 케이스면) `get_optional_params`의 elif 분기 ⑦ (특수 케이스면) `get_supported_openai_params.py`의 elif 분기 ⑧ `model_prices_and_context_window.json` 항목 ⑨ 스트리밍이 특수하면 `streaming_handler.py`. 최소 5곳, 통상 7~9곳. "config 클래스 하나 등록하면 끝"이라는 이상에 도달하지 못했다.

## B. 파라미터 매핑의 실태

핵심 파이프라인은 `get_optional_params`(utils.py:3935)다:

1. `pre_process_non_default_params`(utils.py:3782)가 기본값과 다른 파라미터만 추린다.
2. `_check_valid_arg`(utils.py:4008)가 프로바이더의 supported list와 대조한다. 미지원 파라미터 발견 시:
   - `litellm.drop_params is True` 또는 per-call `drop_params=True`면 **`non_default_params.pop(k, None)` — 경고 로그 한 줄 없이 조용히 제거**(utils.py:4034-4036).
   - 아니면 `UnsupportedParamsError(status_code=500, ...)` — **클라이언트 잘못인데 500으로 분류**(utils.py:4038).
3. 그런데 `user`, `stream_options`, `stream`, `n==1`, `max_retries`는 **하드코딩으로 항상 무언 통과**된다(utils.py:4021-4028, "langchain sends n=1 as a default value" 같은 프레임워크 워크어라운드가 코어 검증기에 박혀 있음).
4. 이후 프로바이더별 `map_openai_params` 호출 — generic fallthrough(`elif provider_config is not None:`)가 존재함에도 **43개의 프로바이더 elif 분기가 여전히 하드코딩**되어 있다.

**이 파일에서 그대로 발견한 회귀 버그 3건**:

- utils.py:4066-4078: `AnthropicTextConfig().map_openai_params(...)`가 **동일 인자로 두 번 연속 호출**됨. 거대 elif 체인의 복붙 사고가 그대로 출하됨.
- utils.py:3816-3818: `if "tools" in non_default_params and isinstance(non_default_params, list):` — `non_default_params`는 dict이므로 **항상 False인 데드 코드**. 주석엔 "fixes #4933"(Gemini의 `additionalProperties: false` 제거)이라 적혀 있으나 이 경로로는 영원히 실행되지 않는다.
- utils.py:3885-3912: `custom_llm_provider == "ollama" and custom_llm_provider != "azure" and ... (16개 != 체인)` — 이미 "ollama"와 같음을 확인한 뒤 다른 값이 아님을 16번 재확인하는 무의미 조건.

**설계가 만드는 사용자 피해**: drop_params의 "조용한 드롭"은 관측 불가능하다 — 응답 어디에도 "seed는 드롭됐음"이 표시되지 않는다. 사용자는 Anthropic에 `seed`를 보냈다고 믿지만 실제론 무시된다. 게다가 drop 판정 지점이 4겹이다: 전역 `litellm.drop_params` / per-call `drop_params` / `additional_drop_params` / opt-in 화이트리스트 `allowed_openai_params`, 그리고 각 config의 `map_openai_params` 내부에서 또 개별 판단. 이 다층 구조 때문에 "drop_params를 켰는데도 에러"가 반복 발생 — [#16204](https://github.com/BerriAI/litellm/issues/16204), [#17719](https://github.com/BerriAI/litellm/issues/17719), [#9936](https://github.com/BerriAI/litellm/issues/9936), [#28132](https://github.com/BerriAI/litellm/issues/28132).

**반대편 구멍**: OpenAI 파라미터 이름이 *아닌* 미지의 kwargs는 검증 자체가 없다. `add_provider_specific_params_to_optional_params`(utils.py:4536)는 OpenAI-호환 프로바이더면 `extra_body`로, 그 외 프로바이더면 **`optional_params`에 그대로 병합**한다. 이후 `transform_request`가 `data = {"model": ..., "messages": ..., **optional_params}`(anthropic transformation.py:1942)로 전개하므로 오타 난 파라미터명이 그대로 와이어에 실려 프로바이더 400을 유발하거나 조용히 무시된다. 즉 **알려진 파라미터는 조용히 드롭, 모르는 파라미터는 무검증 통과** — 정확히 거꾸로 된 안전장치다.

## C. 고유 기능 노출 — 5가지 서로 다른 메커니즘의 동거

LiteLLM은 프로바이더 고유 기능을 **최소 5가지 비일관 채널**로 넣게 해놨다:

1. **최상위 파라미터 승격**: `thinking`(Anthropic 타입 그대로), `reasoning_effort`, `web_search_options`, `safety_identifier` 등이 `completion()` 시그니처에 직접 존재. `VertexGeminiConfig.get_supported_openai_params`(vertex_and_google_ai_studio_gemini.py:294)는 `"thinking"`을 "supported **openai** params"로 반환한다 — Anthropic 방언이 내부 표준이 된 증거.
2. **"supported openai params"의 의미 붕괴**: `AnthropicConfig.get_supported_openai_params`(anthropic/chat/transformation.py:436-467)는 `"speed"`, `"context_management"`, `"cache_control"`, `"thinking"`을 반환한다. OpenAI에 존재하지 않는 이름들이다. 이 리스트는 이제 "OpenAI 파라미터"가 아니라 "우리가 아는 파라미터" 목록이다.
3. **메시지 내부 확장 필드**: `cache_control`은 OpenAI 메시지의 content block 안에 심는다 (factory.py의 `add_cache_control_to_content`, anthropic_messages_pt:2431 등). assistant 메시지에는 `thinking_blocks`/`reasoning_content`가 확장 필드로 붙는다 (`Message` 타입, types/utils.py:1246 — None이면 `del self.thinking_blocks`로 **속성을 지워서** OpenAI처럼 보이게 하는 핵 포함, types/utils.py:1318-1326).
4. **tools 배열 속 가짜 도구**: Gemini의 `googleSearch`, `googleSearchRetrieval`, `enterpriseWebSearch`, `urlContext`, `code_execution`은 OpenAI `tools` 리스트에 특수 이름 항목으로 넣으면 변환기가 알아채는 방식 (vertex_and_google_ai_studio_gemini.py:563-710).
5. **kwargs/extra_body 무검증 통과 + beta 헤더 매핑**: B에서 설명한 blind passthrough. Anthropic beta 기능은 `extra_headers`의 `anthropic-beta`를 `litellm/anthropic_beta_headers_config.json`(프로바이더별 헤더 지원 여부 매핑 테이블)으로 필터링한다 — 이 선언적 테이블 자체는 좋은 아이디어다.

응답 방향에서는 `provider_specific_fields`(citations, web_search_results 등)가 `Message`/`Delta`에 붙는다. 문제는 **요청↔응답 라운드트립이 비대칭**이라는 것: 응답의 `provider_specific_fields.web_search_results`를 다음 턴 히스토리에 넣으면 factory가 이를 재해석해 Anthropic 블록으로 복원해야 하는데, 이 "multi-turn reconstruction"은 이슈 대응으로 하나씩 덧댄 것이다(handler.py:846-869의 [#17737](https://github.com/BerriAI/litellm/issues/17737), [#18137](https://github.com/BerriAI/litellm/issues/18137) 참조 주석).

**대화 중간 프로바이더 전환(우리 목표 2)의 실패 사례가 코드에 화석처럼 남아 있다**:
- `_is_unsignable_thinking_block`(factory.py:2324-2341): Anthropic은 thinking signature를 암호학적으로 검증하므로, 서명 없는 thinking block(타 프로바이더/오픈소스 모델 출신)은 **조용히 드롭**된다. thinking은 프로바이더 간 이식 불가능한 상태 데이터인데 OpenAI-형 메시지에 평문 필드로 넣었기 때문에 생기는 문제.
- `AnthropicConfig.transform_request`(transformation.py:1810-1821): 히스토리의 마지막 tool_calls assistant 메시지에 thinking_blocks가 없으면 `thinking` 파라미터를 통째로 드롭 — 단 `litellm.modify_params=True`일 때만. 관련 이슈 [#18926](https://github.com/BerriAI/litellm/issues/18926), [#14194](https://github.com/BerriAI/litellm/issues/14194), [#15601](https://github.com/BerriAI/litellm/issues/15601).
- 히스토리 정합성 보정이 `modify_params`라는 전역 플래그로 게이팅됨: dummy tool 주입(transformation.py:1800-1801), 빈 user 메시지 placeholder 치환, 연속 같은 role 병합(anthropic_messages_pt), 중복 tool_result 제거 — "히스토리를 어느 프로바이더로도 재생 가능하게"가 일관 설계가 아니라 400 에러 사후 대응의 퇴적층이다.

## D. 스트리밍 정규화

**두 세대가 공존한다.**

구세대 `CustomStreamWrapper`(streaming_handler.py:185)는 프로바이더 raw 청크를 받는 God-object다: `handle_predibase_chunk`, `handle_ai21_chunk`, `handle_azure_chunk` 등 프로바이더별 파서 메서드가 래퍼 클래스 안에 있고, `_dispatch_provider_chunk`(line 1176)가 또 하나의 거대 elif 체인이다. Vertex 함수 호출 감지는 **예외 메시지 문자열 매칭**으로 한다: `if "Part has no text." in str(e):`(line 1300).

신세대는 provider별 `ModelResponseIterator`(예: anthropic/chat/handler.py:518)가 SSE를 `ModelResponseStream`(OpenAI chunk 형)으로 변환하고 CustomStreamWrapper는 후처리(finish_reason 위치 조정, usage-only 청크 제어)만 한다.

**OpenAI chunk로 눌러 담으며 생기는 구조적 손실** (anthropic handler 실측):
- `# Always use index=0 for OpenAI choice format (fixes multi-choice errors)`(handler.py:766-767) — Anthropic content block index를 버리고 전부 choice 0으로 평탄화. `content_block_start/stop` 경계 이벤트는 소멸.
- thinking/signature는 비표준 `Delta.thinking_blocks`로, server tool 결과들은 `provider_specific_fields`에 **누적 리스트를 매 청크 재전송**하는 방식으로 실린다(handler.py:855-869).
- 빈 tool 인자는 `content_block_stop`에서 `arguments="{}"`로 날조(handler.py:877-885), server_tool input 조립 실패는 `except (json.JSONDecodeError, TypeError): pass`(handler.py:898)로 삼켜진다.
- `chunk_creator`의 광역 `except Exception`은 델타 파싱 실패 시 **빈 `Delta()`로 대체하고 계속 진행**(streaming_handler.py:1575-1591) — 콘텐츠 소실이 에러가 아니라 빈 청크로 나타난다.
- streaming_handler.py:1552: `hasattr(t, "functions")`를 체크하고 `t.function`에 접근 — 오타로 인해 죽은 방어 코드.

**근거 있는 알려진 문제들**: finish_reason이 프로바이더별로 다른 청크 위치에 등장([#13348](https://github.com/BerriAI/litellm/issues/13348)); finish_reason 이후 도착하는 usage-only 청크 폐기([#25389](https://github.com/BerriAI/litellm/issues/25389)); 비표준 finish_reason이 pydantic ValidationError 유발([#22671](https://github.com/BerriAI/litellm/issues/22671)); Gemini 스트리밍이 tool_calls 대신 "stop" 반환([#22900](https://github.com/BerriAI/litellm/issues/22900)); text+tool 혼합 응답에서 tool_calls 델타 소실([#17246](https://github.com/BerriAI/litellm/issues/17246)). 별도로 `stream_chunk_builder`(main.py:8529 + streaming_chunk_builder_utils.py 1,042줄)가 로깅/코스트용으로 청크를 재조립하는데, 이는 응답 의미론의 **두 번째 구현**이라 본선과 어긋나는 지점이 계속 생긴다.

## E. 타입/테스트 문제

**dict 파이프라인이 시스템의 혈관이다.** `optional_params` dict가 `map_openai_params` → `transform_request` → `data = {**optional_params}`로 흐르며, 내부 조율용 키가 dict에 남으면 그대로 JSON body가 된다. 코드 주석이 이를 자백한다: tool-name 매핑을 `optional_params`에 두면 "`serialized into the request body via data = {**optional_params}` and would 400 with `Extra inputs are not permitted`"(anthropic transformation.py:1405-1414). 그래서 `is_vertex_request`, `client_metadata`, `json_mode` 같은 내부 키를 전송 직전에 `pop`으로 하나씩 제거한다(transformation.py:1925-1926) — 잊으면 곧장 프로바이더 400. 이 클래스의 버그는 mypy/pyright가 잡을 수 없다.

한 번의 정독에서 나온 출하된 버그 3건(중복 map 호출, 항상-False isinstance, hasattr 오타)이 이 구조의 회귀 특성을 보여준다: **거대 elif + dict 변환 + 광역 except = 조용히 틀리는 코드**.

**테스트 구조**: 2,808개 테스트 파일. 주목할 만한 것은 `tests/llm_translation/base_llm_unit_tests.py`의 `BaseLLMChatTest`(43개 테스트 메서드) — 프로바이더별 테스트가 이를 상속해 conformance suite를 공짜로 얻는 패턴으로, 이건 배울 점이다. 실 API 호출 문제는 VCR(record/replay) + Redis 캐시 cassette(`tests/_vcr_conftest_common.py`)로 완화하지만, conftest 주석에 따르면 litellm import 자체가 `raw.githubusercontent.com`에서 model cost map을 **네트워크로 가져오는** 부작용이 있어 cassette를 오염시켰다(~1900개 중 ~710개). 또한 `mock_response`/`mock_tool_calls`/`mock_timeout`이 **프로덕션 `completion()` 본체에 내장**되어 있다(main.py:5461) — 테스트 심이 제품 코드에 산다. 한계: 스트리밍 청크 순서/타이밍 같은 시간축 동작, 프로바이더 API의 실변경(스키마 추가)은 cassette로 못 잡고, 위 finish_reason류 이슈들이 실사용에서 계속 터지는 이유가 된다.

## F. 그래도 배울 것

1. **BaseConfig 인터페이스 자체는 올바른 모양이다**: `get_supported_openai_params` / `map_openai_params` / `transform_request` / `transform_response` / `get_error_class` / `get_model_response_iterator` / `sign_request` / `should_fake_stream` — 프로바이더 어댑터가 구현해야 할 관심사 목록으로서 검증된 체크리스트다. 139개 프로바이더를 감당한 힘이 여기서 나왔다. `should_retry_llm_api_inside_llm_translation_on_http_error`(azure_ai가 422 시 요청 변형 후 재시도) 같은 훅은 실전에서만 나오는 요구사항이다.
2. **`model_prices_and_context_window.json` — 3,059개 모델의 커뮤니티 유지 레지스트리.** 단순 가격이 아니라 `cache_creation_input_token_cost_above_1hr`, `input_cost_per_token_above_200k_tokens` 같은 다단계 요금, `supports_reasoning`/`supports_prompt_caching`/`supports_native_structured_output` 등 capability 플래그, `deprecation_date`, `prompt_cache_min_tokens`까지. capability 플래그가 실제 동작을 게이팅한다(`supports_reasoning(model)`이 thinking 파라미터 허용 결정). **이 데이터 자산이 LiteLLM의 최대 해자다.**
3. **공유 conformance test suite** (`BaseLLMChatTest` 상속 패턴): 어댑터 N개에 대해 동일 시나리오(tool call, JSON mode, PDF, prompt caching, reasoning)를 강제하는 구조.
4. **`anthropic_beta_headers_config.json`**: 기능 플래그 × 프로바이더 지원 여부를 선언적 테이블로 — null이면 명시적 미지원. 코드가 아닌 데이터로 capability를 기술하는 방향.
5. **프록시 기능 레이어**: virtual key/team/budget(`proxy/auth/budget_throttle.py` 등), JWT/OAuth, spend tracking(가격 맵과 연동), `router.py`의 fallback/cooldown/load-balancing. 그리고 결정적으로 — **OpenAI 허브로 다 안 된다는 걸 스스로 인정하고 `/v1/messages` Anthropic 네이티브 passthrough를 병설**했다(`proxy/anthropic_endpoints/`, `llms/anthropic/experimental_pass_through/`). 게이트웨이는 정규화 경로와 네이티브 경로를 모두 제공해야 한다는 교훈.
6. **Bridge 패턴**(`llms/base_llm/bridges/completion_transformation.py`, `completion_extras/responses_api_bridge`): 엔드포인트 형(chat ↔ responses) 간 변환을 별도 어댑터 계층으로 분리한 것.

## G. 반면교사 종합 — "이렇게 하면 안 된다" 설계 결정 목록

1. **살아있는 외부 API 포맷(OpenAI)을 내부 표현으로 쓰지 마라.** 표현력이 부족해지는 즉시 확장 필드(`thinking_blocks`, `cache_control`, `provider_specific_fields`), 승격 파라미터(`thinking`), 가짜 도구(`googleSearch` in tools)가 각기 다른 규칙으로 증식하고, "supported openai params"라는 개념 자체가 무의미해진다. 내부 IR은 자체 정의하고 OpenAI/Anthropic 포맷은 **가장자리의 어댑터 중 하나**여야 한다.
2. **파라미터 조용한 드롭을 기본 메커니즘으로 두지 마라.** 드롭하되 응답 메타데이터에 `dropped_params: [...]`를 반드시 실어라. 그리고 미지원 파라미터 에러는 4xx다 — LiteLLM은 500을 던진다(utils.py:4038-4040).
3. **검증의 비대칭을 만들지 마라.** LiteLLM은 아는 파라미터는 드롭하고 모르는 파라미터는 무검증 통과시킨다. 반대로: 모르는 키야말로 명시적 네임스페이스(`provider_options.anthropic.*` 식)에 격리하고 스키마 검증하라.
4. **generic fallthrough를 만들고도 특수 분기를 남기지 마라.** 리팩토링은 이주 완료가 기준이지 신규 경로 추가가 기준이 아니다.
5. **조율 상태를 요청 페이로드 dict에 섞지 마라.** `data = {**optional_params}` 때문에 내부 키를 pop으로 청소하는 구조는 "잊으면 400"이다. 요청 빌더는 타입 있는 구조체 → 직렬화 단계에서만 wire 포맷 생성.
6. **프로바이더 상태 데이터(thinking signature, tool_use id, cache 위치)를 무설계로 히스토리에 평문 저장하지 마라.** 전환 시 어떤 블록이 이식 가능/불가능한지(서명 검증 실패 → 드롭? 에러? 재요약?)를 **명시적 정책**으로 설계하라. LiteLLM은 조용한 드롭 + `modify_params` 전역 플래그로 얼버무렸고, 그 결과가 #14194/#15601/#18926의 400 지옥이다.
7. **스트림 정규화에서 이벤트 경계를 버리지 마라.** content block start/stop, block index를 버리면 다중 블록/다중 choice/서명 전달이 전부 후속 핵이 된다. 내부 스트림 이벤트 모델은 상위 집합(superset)이어야 하고, OpenAI chunk는 다운샘플링 출력 중 하나여야 한다.
8. **finish_reason/usage의 위치·유무를 프로바이더 우연에 맡기지 마라.** "종료 청크에 무엇이 실리는가"를 내부 계약으로 고정하고 어댑터가 이를 보장하게 하라 (#13348, #25389).
9. **파싱 실패를 광역 except로 삼켜 빈 델타로 대체하지 마라** (streaming_handler.py:1575-1591). 데이터 소실은 시끄럽게 실패해야 한다.
10. **문자열 매칭으로 제어 흐름을 만들지 마라** (`"Part has no text." in str(e)`).
11. **거대 단일 파일을 허용하지 마라.** main.py 9천 줄/utils.py 9.6천 줄은 그 자체가 복붙 중복 호출 같은 사고의 배양지다.
12. **테스트 편의 코드(mock_response)를 프로덕션 핫패스에 넣지 마라.** 또한 라이브러리 import가 네트워크 fetch(모델 가격 맵)를 하게 하지 마라.
13. **동적 dict 변환 구조라면 회귀는 필연이다.** 항상-False isinstance 같은 버그는 타입 시스템이 있는 언어(또는 전면 스키마 검증)면 컴파일 타임에 죽는다.

## 우리 게이트웨이에 가져올 것

- `BaseConfig`의 메서드 목록을 어댑터 인터페이스 설계의 체크리스트로 (param mapping / request / response / error / stream iterator / signing / fake-stream 판단 / retry-with-transform 훅)
- `model_prices_and_context_window.json`류의 **모델 레지스트리: 가격 다단계 + capability 플래그 + deprecation, 그리고 capability가 런타임 동작을 게이팅하는 구조** (데이터 자체를 차용하는 것도 고려 — MIT)
- `anthropic_beta_headers_config.json`식 선언적 기능×프로바이더 지원 매트릭스
- 프로바이더 공통 conformance test suite (상속/파라미터라이즈로 N개 어댑터에 동일 시나리오 강제) + record/replay
- 정규화 API와 **네이티브 passthrough의 병설** (LiteLLM조차 결국 `/v1/messages`를 따로 열었다)
- 프록시 기능 레이어의 요구사항 목록: virtual key, team/budget, spend tracking, fallback/cooldown 라우팅, 오버헤드 계측 헤더(`x-litellm-overhead-duration-ms`)
- 엔드포인트 형 변환을 별도 Bridge 계층으로 분리하는 발상

## 피할 것

- OpenAI 포맷을 내부 IR로 쓰는 것 (→ 자체 superset IR, 프로바이더 상태 블록을 1급 타입으로: thinking signature, cache point, tool_use id에 origin-provider 태그)
- 파라미터 조용한 드롭 (→ drop 시 응답 메타에 보고, 미지원은 4xx)
- 미지의 kwargs 무검증 passthrough (→ 네임스페이스 격리 + 스키마)
- 디스패치 거대 분기문과 부분 이주의 장기 공존
- 요청 dict에 내부 키 혼입 (`data = {**optional_params}` 패턴)
- 스트림 이벤트 경계/인덱스 파괴, finish_reason/usage 위치의 프로바이더별 우연 의존
- 광역 except로 빈 델타 반환, 예외 메시지 문자열 매칭
- `modify_params`/`drop_params` 같은 전역 가변 플래그로 히스토리 변형 정책을 결정하는 것 (→ 요청 단위 명시 정책)
- 9천 줄 파일, 테스트 심의 프로덕션 침투, import 시 네트워크 의존
